# 云托管部署指南（后端 Express 服务）

前端 `index.html` 走静态网站托管，后端 `server/` 走云托管——**两个独立服务，同一个仓库**。静态托管不会运行 Node 代码，所以后端必须单独建一个服务。

已经有静态托管在跑了也没关系：两个服务互不影响，随时可以补建后端，不用重传前端。

---

## 第 1 步：建数据库集合

云开发控制台 → 数据库 → 新建集合 `chat_messages`。

权限建议选 **「仅管理端可读写」**（后端用管理员身份访问，不受这条规则限制）。

> 为什么可以收紧：后端模式下前端不再直连数据库，所有读写都经过 `server/index.js`。收权之后，即使有人拿到你的环境 ID 也读不到数据——这正是加后端的主要收益。
>
> 如果你还想保留「前端直连云数据库」的备用模式（`env` 那条路），权限就得留「所有用户可读写」，两种模式的取舍自己定。

---

## 第 2 步：新建云托管服务

云开发控制台 → 云托管 → 新建服务，按下表填：

| 字段 | 填什么 | 说明 |
|---|---|---|
| 服务名称 | `chatroom-api` | 随意，控制台显示用 |
| 部署方式 | 代码仓库 / Git 部署 | 和静态托管一样授权 GitHub |
| 仓库 | `Cxily117/chatroom` | 分支 `main` |
| **目标目录** | **`server`** | ⚠️ 最关键的一项，不能填 `/` |
| 端口映射 · 访问端口 | `80` | 对外 HTTP 端口 |
| 端口映射 · 服务端口 | `80` | 与 `Dockerfile` 里 `EXPOSE 80`、`ENV PORT=80` 一致 |
| 实例规格 | 最小规格（0.25 核 0.5G） | 课堂演示足够 |
| 最小实例数 | `0`（允许缩到 0 省钱） | 缺点是首次访问有冷启动，约 2~5 秒 |

目录填 `server` 的原因：仓库根目录是前端，`Dockerfile` 和 `package.json` 都在 `server/` 里，填错会构建失败。

---

## 第 3 步：配环境变量

同一页面的「环境变量」里加这几项：

| 变量名 | 值 | 必填 |
|---|---|---|
| `TCB_ENV` | 你的环境 ID，如 `slim-galliform-d1gct7tprfa85b9d8` | ✅ |
| `DB_DRIVER` | `cloudbase` | ✅（不填会退回文件存储，容器重建就丢数据） |
| `COLLECTION` | `chat_messages` | 可选，默认就是这个 |
| `TOKEN_SECRET` | 一串随机字符，越长越好 | ✅ 建议改，默认值是公开的 |
| `PORT` | `80` | 可选，镜像里已设 |
| `ALLOW_ORIGIN` | 你的前端域名，如 `https://xxx.tcloudbaseapp.com` | 可选，不填等于放开所有来源 |

`TOKEN_SECRET` 生成一串随机的就行，例如：

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

---

## 第 4 步：部署并自测

点「部署」，等镜像构建完成（首次一般 2~4 分钟）。拿到访问域名后，先打健康检查：

```bash
curl https://你的服务域名/api/health
```

预期返回：

```json
{"ok":true,"driver":"cloudbase","collection":"chat_messages","users":0,"messages":0,"uptime":5}
```

- `"driver":"file"` → `DB_DRIVER` 没生效，回去检查环境变量；
- 502 / 超时 → 端口填错了，或容器启动失败，去「日志」看报错。

再验一次注册：

```bash
curl -X POST https://你的服务域名/api/register \
  -H "Content-Type: application/json" \
  -d "{\"account\":\"test01\",\"password\":\"123456\",\"nickname\":\"测试\"}"
```

能在控制台数据库里看到一条 `kind=profile` 的记录，说明整条链路通了。

---

## 第 5 步：让前端指向后端

改 `index.html` 顶部配置：

```js
window.CHAT_CONFIG = {
  apiBase: 'https://你的服务域名',   // ← 填这里，结尾不要带斜杠
  env: '',                          // 走后端时这一项留空即可
  ...
};
```

提交推送后，静态托管会自动重新构建上线（Git 部署模式下不用手动传文件）。打开页面，右上角徽章应该从「💾 本地存储」变成 **「🌐 后端 API」**。

如果徽章还是本地存储，页面提示会直接写出原因（例如「后端不可达：连不上后端」），按提示查：

| 现象 | 原因 |
|---|---|
| 后端不可达 | 域名写错、服务没起来、或容器冷启动还没就绪 |
| 一直转圈 | `apiBase` 结尾多了斜杠导致路径拼成 `//api/health` |
| 控制台报 CORS | `ALLOW_ORIGIN` 配了具体域名但和实际访问域名不一致，先清空它 |
| 能打开页面但注册报错 | 后端起来了但 `DB_DRIVER=cloudbase` 权限/凭证有问题，看服务日志 |

---

## 部署完的分工

| 改什么 | 怎么生效 |
|---|---|
| 前端 `index.html` | push 到 `main` → 静态托管自动重建 |
| 后端 `server/*.js` | push 到 `main` → 云托管自动重建镜像 → 新版本容器 |
| 数据库结构 | 不用改表，字段随写入自动生成 |

两个服务都跟着 `main` 走，所以以后你说一句「改好了」，push 完就自动上线，不需要你再点任何按钮。

---

## 费用提醒

- **静态托管**：存储 + CDN 流量，有免费额度，没人访问不产生费用。
- **云托管**：按容器实例的 CPU / 内存 / 运行时长计费。最小实例数设 0 时，没人访问不产生实例费用，但会有冷启动；设 1 则一直常驻，费用高一点但打开即用。
- 课堂演示建议：先设 0，演示前 1 分钟打开一次页面把容器热起来。
